# WareTwin 后台设施与容器管理开发说明

整理日期：2026 年 11 月 26 日。更新日期：2026 年 11 月 27 日。后台入口：`/workspace`。前期背景见 [3D 仓库可视化改造方案会议](3D仓库可视化改造方案会议.md)。

本轮改造将后台的“货架”分类改为“设施”，建立先定义容器、再配置货架或地面库位的建模流程，同时增加设备模型、编号、安装或停靠位置，以及按速度或按生产时间计算作业耗时的配置。已有 AGV、提升机、流水线与用户新增设备统一归入设备类别及模型目录。首期使用内置简模，暂不依赖已有的大体积原始 GLB；先把人工创建与三维生成做完整，再接入 CAD 和表格导入。下文按本轮确认的业务规则编写，第十二节汇总实施口径。

## 一 设施分类与操作流程

“设施”下提供四个入口：添加容器、添加货架、添加库位、添加设备。

| 入口 | 管理内容 | 是否具有摆放坐标 | 主要关联 |
| --- | --- | --- | --- |
| 添加容器 | 有名称、类型、颜色和实际尺寸的容器模板 | 否 | 供货架和地面库位选择 |
| 添加货架 | 货架结构、层数、层板及连续组数 | 是 | 绑定容器，生成相应的存放位置 |
| 添加库位 | 没有货架、直接在地面放置容器的存储位置 | 是 | 绑定容器，支持行列批量生成 |
| 添加设备 | AGV、提升机、流水线及新增设备的类别、编号、布置姿态和耗时方式 | 是 | 使用统一模型目录，为后续 Odoo 动作或状态消息预留标识 |

创建流程为：先建立容器模板，再创建货架或地面库位并选择容器，预览模型后保存。设备可以独立添加，不依赖容器。

点击添加按钮后弹出对应表单。选中已有对象时，右侧“选中对象”显示该类型的可编辑属性。容器模板的属性中不出现 X、Z、旋转和摆放楼层。

当前“点击添加货架未成功”的现象需要复现并修复，不能直接认定唯一原因是缺少容器。若未选择仓库、没有可用容器或当前版本已发布，应显示具体原因。已发布版本保持只读，并提供明确的“复制为草稿后编辑”提示。

## 二 添加容器

容器是可复用的尺寸和外形定义，不是独立摆放在地图上的物体。其位置和朝向由所绑定的货架格位或地面库位决定。

| 字段 | 要求 |
| --- | --- |
| 名称 | 必填，用于绑定和导入匹配；例如“塑料托盘 1100”“木托盘 1200” |
| 类型 | 首期提供塑料托盘、木托盘、塑料箱 |
| 颜色 | 塑料托盘、塑料箱可以选择；木托盘使用固定木色，不提供颜色选择 |
| 宽度 | 容器本体的实际宽度，单位米 |
| 深度 | 容器本体的实际深度，单位米 |
| 高度 | 容器本体的实际高度，单位米 |

类型结构保留扩展能力，金属托盘可以后续增加，不作为首期必须提供的第四种类型。同一种类型允许建立多个不同尺寸和颜色的模板；一个仓库可以同时使用多种模板，不能限制整个仓库只能选择一种容器。

一个货架组按创建时选择并绑定的容器建模，该组所有层和格位统一使用这一种容器。不同货架组、不同地面库位可以绑定不同模板；同一仓库允许多种容器，不增加同组货架按层或按格混放的设置。

容器模板在同一组织下共用，该组织的多个仓库可以直接选择同一模板，不按仓库重复创建。名称在组织内应能唯一匹配；内部使用稳定 ID 引用，导入时在当前组织内把容器名称解析为对应 ID。其他组织的模板不进入当前组织的选择和导入范围。重名必须提示用户处理，不能随机匹配。已被引用的容器不能直接删除而留下无效引用。

容器尺寸必须为有限正数。修改被引用模板的尺寸时，应重新校验其绑定的货架和库位；已发布布局保留发布时的容器定义，不能随模板修改而改变历史布局。

木托盘、塑料托盘和塑料箱应能通过外形识别。三维尺寸以表单数值为准，不再随机生成容器大小。容器本体高度与货物堆高分开：托盘高度不能被当成托盘上货物的高度。

## 三 添加货架

横梁式高位货架和 CTU 料箱货架使用统一的创建流程，通过容器、层板和底层选项体现差异。

| 字段 | 要求 |
| --- | --- |
| 名称或编号前缀 | 用于区分生成的货架组及其存放位置，支持自动编号 |
| X、Z | 当前楼层内本排货架的网格外框起点，与地面库位一致 |
| 宽度 | 单组左右立柱的中心距，单位米；净宽、外廓宽度及整排总宽由系统自动换算 |
| 深度、高度 | 单组货架尺寸，单位米，不是整排总尺寸 |
| 旋转角度 | 整排朝向，二维编辑和三维展示必须一致 |
| 绑定容器 | 必选，从同一组织下的容器模板中选择；该组统一使用此容器 |
| 每层容器数量 | 只读计算结果，系统沿货架宽度计算能放下的最大数量 |
| 层数 | 可存放容器的层数，必须为正整数 |
| 是否有层板 | 控制有横梁的层位是否安装层板 |
| 是否有底层 | 控制地面这一层是否安装横梁，以及相应层板 |
| 行组数 | 一排连续生成多少组货架，默认一组 |

每层容器数量由系统根据立柱内侧净宽和绑定容器的宽度自动计算。宽度或绑定容器变化后，数量和均匀间隙一起重新计算，不能沿用“每层固定两个”的写死逻辑。

### 层数与底层的含义

“三层”始终表示有三个可以存放容器的空间。是否安装底层横梁和层板，不改变存放层数。

| 三层货架的选择 | 横梁所在层位数量 | 层板数量 | 第一层容器的支承位置 |
| --- | --- | --- | --- |
| 有层板、有底层 | 3 | 3 | 底层层板 |
| 有层板、无底层 | 2 | 2 | 地面 |
| 无层板、有底层 | 3 | 0 | 底层横梁 |
| 无层板、无底层 | 2 | 0 | 地面 |

表中的横梁层位每层包含前后两根横梁。选择“有层板、无底层”时，只取消地面层的梁和板，上面的层板仍保留。

初版按总高度和层数等分空间。例如货架高 3 米、三层，名义层间距为 1 米；容器是否放得下，还应扣除实际梁板占用，并校验容器高度及需要展示的货物堆高。不能把“三层”实现成“另外三层再加一个地面层”。

### 连续创建多组

行组数为 10 时，一次生成同一排连续的 10 组货架，整排随起始位置和角度摆放。创建后允许逐组选择和修改，首期不要求将整排做成必须整体编辑的一个块。

连续组按立柱中心距排列，连接处的立柱框架不重复绘制。设单组中心距为 `w`、立柱宽度为 `t`、组数为 `G`，整排外廓宽度自动计算为 `G × w + t`；不能把每组外廓宽度简单相加，否则会重复计入连接处立柱。

## 四 货架与容器的建模约束

### 现有尺寸基线

当前 [RackInstances.tsx](../frontend/src/components/scene/RackInstances.tsx) 中，立柱截面为 100 × 100 mm，横梁高 100 mm、厚 80 mm，层板厚 40 mm。横梁和层板虽然分别生成，但共用渲染批次。改造后至少要能分别控制层板的生成与底层梁板的生成；是否拆成独立渲染批次，由实现决定。

货架宽度 `w` 确定为左右立柱中心距，立柱宽度记为 `t`。系统自动换算：

```text
单组内侧净宽 W_clear = w - t
单组外廓宽度 W_outer = w + t
连续 G 组的整排外廓宽度 = G × w + t
```

按当前 0.1 米宽的立柱计算，净宽为 `w - 0.1`，单组外廓宽度为 `w + 0.1`。表单明确标注“宽度（立柱中心距）”，净宽和外廓尺寸作为计算结果展示，不让用户重复填写。

货架与库位均以网格外框起点定位。货架的立柱中心、内侧边界与外框起点不是同一个位置，建模时要计入半柱宽偏移；兼容旧布局时转换参考点，保持原有设施的实际位置。

### 水平方向均匀排布

先计算两侧立柱内侧之间的可用净宽，再按所选容器的实际宽度计算。设：

- `W_clear` 为货架内部可用净宽。
- `c` 为单个容器宽度。
- `n` 为系统自动计算的该层最大容器数量。
- `g` 为两侧与中间均匀分配的间隙。

先按尺寸计算最大整数数量，再把剩余空间均分到左右两侧及容器之间：

```text
n = floor(W_clear / c)
g = (W_clear - n × c) / (n + 1)
第 i 个容器中心 = 左侧内边界 + g + c / 2 + i × (c + g)
i = 0 ... n - 1
```

例如，立柱中心距为 2.5 米、立柱宽 0.1 米时，净宽为 2.4 米，单组外廓宽度为 2.6 米。绑定宽 1 米的容器，系统自动计算每层最多两个，左、中、右三处间隙各约 0.1333 米。

容量计算以实际尺寸能够放入为准，净宽恰好等于容器总宽时，均分间隙为零。计算使用统一的尺寸精度，避免浮点误差造成整除场景少算一个容器。`n < 1` 或容器深度、高度不满足设施条件时，提示调整尺寸或容器，不能缩小模型假装放得下。

### 深度与旋转

容器在货架可用深度内前后居中。先计算立柱或其他结构是否占用有效深度，再校验容器深度，不以整架深度代替有效空间。

先在货架自身的局部坐标中计算梁、板、容器和存放中心点，再对整组执行同一旋转和平移。不能只旋转二维外框，而三维容器仍按未旋转坐标摆放。0° 时，X 方向为宽度，Z 方向为深度及 AGV 接近取货的方向；角度规则沿用当前约定，旋转后取放方向随设施一起旋转。

## 五 添加地面库位

这里的“库位”是没有货架、在地面直接放置容器的存储位置。库位定义允许占用的区域，容器模型按自身尺寸放在区域中心。

| 字段 | 要求 |
| --- | --- |
| 名称或编号前缀 | 用于自动生成各库位名称 |
| X、Z | 本批库位的网格外框起点，与货架一致，不是首格容器中心 |
| 宽度、深度 | 单个库位的占地尺寸，单位米 |
| 旋转角度 | 库位取放朝向，并作用于整批排布 |
| 容器 | 必选，从同一组织下的模板选择，使用其名称、类型及尺寸 |
| 行组数、列组数 | 正整数，生成数量等于行数乘列数 |
| 货物显示高度 | 可选；如保留高度输入，应表达货物堆高，不能误写成库位本身高度 |

行数、列数都为 10 时，一次生成 100 个库位。每个库位有自己的稳定 ID、业务名称、中心点和朝向，创建后可以单独选择和修改。

0° 时，列沿 X 方向排列，行沿 Z 方向排列。设网格外框起点为 `(x0, z0)`，单格宽深为 `W、D`，从零开始的列号、行号为 `col、row`，则：

```text
库位中心 X = x0 + (col + 0.5) × W
库位中心 Z = z0 + (row + 0.5) × D
网格总宽 = 列数 × W
网格总深 = 行数 × D
```

这些中心也是容器的摆放中心和以后对接的库位点。非零旋转时，以同一个外框起点对整批网格及其中心点统一旋转，取放方向同步变化。

例如库位为 1.3 × 1.3 米、容器为 1.1 × 1.1 米，容器居中后四侧各留 0.1 米。库位小于容器或不满足确定的边距要求时，应阻止保存并说明原因。

批量生成时，库位宽深决定网格节距，容器周围的留白属于库位内部。需要留出通道时通过设施排布或明确的排间距处理，不能把容器边距当成 AGV 通道。

手动生成的业务名称可采用“区域或批次前缀、行号、列号”的方式。具体编码规则可配置；一旦与 Odoo 点位绑定，不应因重新排序而自动改名。

## 六 添加设备

设备类别统一包括已有的 AGV、提升机、流水线，以及以后新增的设备，不另建一套只供新增 GLB 使用的设备入口。创建时先从统一目录选择具体类别或型号，再建立有独立编号和位置的设备实例。同一类别可以有多台设备，模型资源复用，编号分别维护。

| 字段 | 要求 |
| --- | --- |
| 设备类别 | 从统一设备模型目录选择，包含内置 AGV、提升机、流水线和用户新增模型 |
| 设备编号 | 区分同类别下的多台设备，必填 |
| 显示名称 | 可使用类别名称和编号组合展示 |
| X、Z | AGV 等移动设备的空闲停靠位置；提升机、流水线等固定设备的安装位置 |
| 旋转角度 | 移动设备停靠朝向或固定设备安装朝向 |
| 耗时计算方式 | 二选一：“按运行速度”或“按生产时间” |
| 运行速度 | 选择“按运行速度”时必填，单位 m/s，必须大于零 |
| 生产时间 | 选择“按生产时间”时必填，表示车辆或货物到达指定点位后必须停留的作业时长，可选秒、分钟或小时，必须大于零 |

例如设备类别为 `SFL-CBD20`，编号分别为 `001`、`002`，即可创建两台使用同一车型模型、但具有不同停靠位置的设备；同样可以建立多台不同编号的提升机或多段流水线设备。

AGV 无任务时保持配置的停靠姿态，不自动参与演示随机任务；任务完成后是否自动返回该位置，需要以后按任务规则确定。提升机、流水线维持固定安装位置，分别更新升降平台或输送部件的动作和状态，不能把所有设备都按 AGV 的平面移动方式处理。

提升机原有的服务楼层、升降行程，流水线原有的长度、路径及运行方向等类型专有参数应继续保留，并按所选类别显示。统一设备入口不能使这些配置变成只有 X、Z 和旋转。

### 耗时计算方式

“设备类别”说明采用哪一种模型和设备行为，“耗时计算方式”说明一次运输或作业需要多久。二者分别配置，不使用“设备机身是否移动”来区分速度和时间：提升机、输送线虽然固定安装，平台或货物仍有运输行程，适合按运行速度计算。

| 耗时计算方式 | 表单输入 | 计算规则 | 典型设备 |
| --- | --- | --- | --- |
| 按运行速度 | 运行速度，单位 m/s，例如 0.5 m/s | 行程时间 = 实际行程距离 ÷ 运行速度 | AGV、提升机、输送线 |
| 按生产时间 | 到点后的强制停留时长，例如 5 分钟或 2 小时 | 确认到达后开始计时，满足时长后才允许后续操作 | 充电点、加工设备、打包机、缠绕机及等待点 |

“生产时间”在界面中备注为“到点后的强制停留／作业时间”：车辆或货物到达指定设备或作业点位后，必须在该处停留设定的时长，才能继续相应的下一步操作。这个参数适用于充电、加工、包装、缠绕和等待，不要求一定制造出新的货物；它不是“每小时生产多少托”的产出速率。

计时以车辆到达确认或货物交接到位为起点，不能在任务创建或派发时提前开始。用于调度计算时：

```text
最早可继续时间 = 确认到达时间 + 生产时间
```

未满足停留时长时，相应车辆不能继续离开，或相应货物不能被执行下一次取走；后续任务的最早执行时间不得早于最早可继续时间。停留约束作用于对应车辆或货物，不自动冻结整个仓库。

| 场景 | 停留对象与放行条件 |
| --- | --- |
| 车辆充电 | AGV 到达充电点后停留 2 小时；在仿真调度中，满足该充电时长后才允许车辆执行后续任务 |
| 货物加工或等待 | 货物被送到指定设备点位后停留 2 小时；满足时长后才允许安排后续取货执行 |

货物需要停留，不自动意味着完成卸货的 AGV 也要陪同等待；车辆是否继续占用由该项作业规则决定。

按运行速度计算时，不同设备的行程定义如下：

- **AGV：** 使用实际规划路线的长度，不用起终点直线距离替代绕行距离。
- **提升机：** 使用本次起止位置的升降行程，不能直接使用整台提升机外形高度。
- **输送线：** 使用货物在输送路径上本次需要经过的长度；有转弯时按路径各段求和。

例如 AGV 以 0.5 m/s 运行，路线长 10 米，匀速行程时间为 20 秒；提升机以 0.5 m/s 升降 3 米，匀速行程时间为 6 秒。按生产时间配置为 5 分钟时，一次作业时长为 300 秒；配置为 1 小时时为 3600 秒。

表单只显示当前方式需要的参数，同一个作业阶段切换方式后不重复计算另一套参数。设备类别可以提供默认方式和默认值，添加具体设备时允许输入和调整，每台设备单独保存，修改一台不影响同型号其他设备。

运输段按运行速度计时，到点作业段按生产时间计时，两者可以在一条流程中先后发生。例如 AGV 先按自身速度驶向充电点，再按充电点配置停留 2 小时；流程耗时包含“行程时间 + 到点停留时间”。两种计算方式不意味着一条完整任务只能有运输或停留其中一段。

内部统一使用米、秒和 m/s 保存计算值，生产时间的单位选择同时保留以便编辑时恢复。禁止零速度、负速度、零或负的生产时间；不能用米每秒的数值直接当作秒，也不能把分钟数未换算就作为秒使用。首期速度法采用匀速行程估算，排队、装卸或开关门若以后纳入，应作为明确的额外作业步骤处理。

这两个参数先用于设备配置和方案中的耗时计算，并为调度保留到达时间、当前停留状态与最早可继续时间。到达触发计时、满足时长后解除相应停留约束的规则已经明确；连续生产、额外入料条件和自动生成示意货物等生产流程后续另行完善。

### 类别与模型目录

所有设备模型归入同一个设备模型库根目录，目录下可以按 `agv/`、`lift/`、`conveyor/`、`custom/` 等子目录组织，但共同使用一个类别清单。后台的“设备类别”从这份统一清单读取，现有设备和用户新增设备使用相同的选择、编号、摆放及保存流程。

设备类别维护稳定的类别编码、名称、设备大类、模型入口，以及可选的默认耗时方式和参数。具体设备的运行速度或生产时间单独保存，不写死在三维模型中。已有 [GLB 清单](../glb/manifest.json) 可以作为外部模型的登记来源，但文件名不应直接代替可长期使用的类别编码。

当前内置 AGV、流水线和提升机分别由 [Robots.tsx](../frontend/src/components/scene/Robots.tsx)、[Fixtures.tsx](../frontend/src/components/scene/Fixtures.tsx)、[Mezzanine.tsx](../frontend/src/components/scene/Mezzanine.tsx) 中的代码生成，不能仅通过扫描 GLB 文件来构造类别列表。统一目录同时登记内置程序化模型和外部 GLB 模型；内置模型的入口及相关定义纳入模型库，保留原有的动作与状态连接。

首期优先把这些内置模型纳入统一设备目录，完成设备选择、编号、布置和耗时参数。其他车型可以先登记类别、使用内置简模或占位外形，真实外观待轻量化后再绑定；类别、编号和后续 Odoo 映射不因外形未就绪而阻塞。外部 GLB 的加载能力按后续模型接入阶段扩展；已有七个原始 GLB 不作为当前功能开发的前置条件。

后续新增设备时，将模型及必要的类别登记信息加入同一模型目录和清单，即可进入后台的设备类别列表，不为每个新型号另写一个添加入口。增加同型号的第二台设备只需填写新编号和位置，不重复上传或复制模型。

模型登记需要明确单位、实际尺寸、朝向、落地原点及必要偏移，保证放入场景后大小和位置正确。GLB 模型还需要浏览器可访问的资源地址；模型较大时应复用加载结果并优化资源，加载失败时保留设备编号和位置，以占位外形提示。

旧布局中的 AGV、提升机和流水线应能映射到统一设备目录，保留原设备 ID、运行配置及后续 Odoo 对接关系，避免重新登记后出现重复设备或设备编号变化。

### 模型资产的开发与运行策略

原始模型、软件运行模型和开发简模分别承担不同用途，统一通过设备目录关联：

| 用途 | 资产与使用方式 |
| --- | --- |
| 日常功能开发 | 默认使用内置程序化简模，按实际配置展示尺寸、位置和朝向；无需下载原始 GLB |
| 原始模型归档 | 七个高精度原文件保留在模型资产 Release，清单保留版本与摘要；不作为默认运行资源或构建输入 |
| 后续真实车型展示 | 挑选需要的车型制作轻量运行版本，通过统一设备目录按需加载，多台同型号设备复用模型资源 |

需要降低的是文件体积和渲染复杂度，不是把真实车型的长宽高缩小。调整场景缩放不能代替模型优化；优化结果仍应保持米制尺寸、朝向、落地位置和需要独立运动的部件。

后续模型处理先检查面数、材质、贴图及绘制开销，再删除不影响展示的内部细节、减少面数、合并合适的重复结构并压缩贴图。几何压缩可采用 Meshopt 或 Draco，纹理可按需要采用 KTX2 等格式；所选格式需与实际 Three.js 版本和加载器配置一起验证。优化时保留货叉、车轮、升降平台等需要独立控制的结构。

文件小并不自动代表运行开销低。接入前需在目标终端验证首次加载、同屏多台设备及运动效果，再确定运行模型预算；不预先保证所有原模型都能压到同一文件大小。

首次下载、替换模型或明确排查文件损坏时执行完整 SHA-256 校验。日常启动、测试、构建、Git 拉取与源码一致性检查不附带全量模型扫描。已通过校验且未更换的模型复用现有文件，避免反复下载和重复人工校验。

当前确认页面尚未加载这些原始 GLB，启动、构建和 CI 也没有调用模型下载或检查脚本。现有本机或 Mac4 上的原文件作为可选缓存保留，不因暂时停用而重新处理。

优化参考：[glTF Transform 工具说明](https://gltf-transform.dev/cli)、[gltfpack 模型优化说明](https://meshoptimizer.org/gltf/)、[Three.js GLTFLoader 压缩格式配置](https://threejs.org/docs/pages/GLTFLoader.html)。

### Odoo 设备识别

按用户要求，设备类别与设备编号共同用于以后 Odoo 下发运动或动作信息时识别设备，该规则覆盖 AGV、提升机、流水线及新增设备。可以展示为 `SFL-CBD20-001`，同时保存独立的类别编码和编号字段，避免仅靠拼接字符串反向解析。

同一站点或仓库中，这个组合必须唯一；跨站点传输时同时携带站点标识。内部实例 ID、设备显示名称与对接标识分别保留，修改显示名称不应让设备失去原来的接口映射。

本轮预留设备映射和初始姿态。实际运动或动作 API 的路径、报文和坐标约定需以后结合 Odoo/WCS 合同确定。AGV 移动、提升机升降和流水线输送使用各自的设备行为；按任务播放的示意动画与真实设备状态分别标明来源，不能将动画推算的位置作为真实车况。

## 七 点位名称与坐标

容器模板没有坐标；货架、库位和设备有坐标。系统内平面使用 X、Z，高度使用 Y，尺寸统一为米，界面旋转角使用度。设施属于当前选择的楼层，三维高度应计入该楼层标高。

导入的存储点位表示容器的中心点，不是货架角点。生成三维外形时，应根据中心、容器尺寸、父级设施尺寸和旋转关系计算摆放位置。

人工创建货架和地面库位时，输入的 X、Z 统一指网格外框起点；生成或导入的库位点则指容器中心，两者需要按尺寸和旋转关系换算。0° 时，所有货架和库位的宽度都沿 X 方向，AGV 沿 Z 方向接近取货；旋转角度及其正负方向沿用现有规则。

CAD 中的 XY 坐标经单位、原点、轴向及旋转校准后映射到场景 X、Z。不能直接把 CAD 的 Y 值作为模型高度，也不能为对齐画面而随意改变真实点距。

批量生成的点位需要可追溯到货架组、层、格位或地面网格。导入已有项目时，原点位名称必须保留，并与 Odoo/AGV 的名称对应；缺少名称或名称冲突时提示处理，不能静默重命名。

## 八 CAD 与表格导入

先完成上述人工建模流程，再增加导入生成，复用相同的尺寸、绑定和校验规则。

1. 先在后台创建并命名容器模板。
2. 导入 CAD 点位及配套表格，读取点位名称、坐标、点位类型和容器名称；涉及多楼层时携带楼层信息。
3. 在当前组织的共享容器库内校验容器名称是否存在并且唯一。缺少或无法匹配容器时阻止自动生成，不能猜测容器尺寸。
4. 完成坐标校准，按容器中心点放置，并结合点距、排列方向和选择的设施模板计算几何关系。
5. 展示生成预览、识别出的分组和未解决的问题，由用户确认后写入草稿。

容器尺寸和点距可以帮助推算排布，但仅有平面中心点不能唯一确定货架的高度、层数、是否有层板、底层形式或连续组的划分。这些参数须来自导入数据、所选货架模板或人工补充。地面库位和货架点位也需要通过点位类型或模板区分。

导入单位不明、点位缺名称、容器未匹配、几何越界或尺寸放不下时，应定位到相应行或对象，允许修正后重试。

## 九 保存与三维展示

容器模板在组织级模板库维护，设施、模板引用和业务点位随布局草稿保存；设备的耗时计算方式、运行速度或生产时间及显示单位一并保存。已发布布局保存绑定模板的尺寸、类型和颜色快照，后续组织模板修改不能改变历史发布结果。保存后重新打开、导出再导入，尺寸、朝向、编号、耗时参数和关联应保持一致。新增数据需纳入布局类型、服务端校验与版本兼容，不能只存在于浏览器临时状态。

二维编辑、三维展示与导航使用同一套设施数据。货架旋转、批量生成和容器替换后，不能只更新编辑器而仍显示旧的演示布局。旧布局缺少新增字段时要有兼容处理，不能因此丢失已保存的仓库。

首期三维展示以容器和设施比例正确、库位清楚、设备位置正确为重点。外墙按不遮挡内部的方向隐藏，仓库边界及越界校验仍保留。

容器模板决定外形和尺寸，不代表该位置一定有库存。实际有货、空位和库存指标以后以 Odoo 的授权数据为准；方案演示可以配置示意占用，但必须与实况区分，不能继续把随机箱子填充当成库存记录。
